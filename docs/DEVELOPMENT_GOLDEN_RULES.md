# 工程开发黄金法则与避坑沉淀 (Development Golden Rules)

这份反思直击核心：犯错并不仅仅是“修好它”，而是要从思维惯性和操作路径上彻底看清根本原因，建立前置避坑机制，实现一次性交付正确结果。

---

## 深刻复盘：为什么会出现这几个错误？

### 1. 操作手段不当（脚本盲目替换 vs 语法边界）
* **深层原因**：为了图快，使用了粗糙的单行正则或字符串替换去修改 TypeScript 复杂对象数组。由于缺少对嵌套闭合括号（`{ { ... } } }`）的上下文感知，造成了语法截断与多余花括号。
* **避坑法则**：后续涉及核心静态数据或复杂配置文件的修改，严禁使用脆弱的单行模糊匹配脚本。要么用完整文件标准覆盖（HereDoc），要么用严谨的 AST 级别的解析，并在每次脚本执行后必须立即在流水线第一步跑类型检查，绝不把残缺语法留给测试阶段。

### 2. 状态遗漏（“写了页面”与“业务上线”割裂）
* **深层原因**：心智模型只停留在“把这个组件写出来、页面跑通”，忽略了架构中早已存在的 `catalog.ts` 集中式目录状态机。把“组件开发”与“系统注册”看成了两件独立的事，导致页面能跑但目录漏掉。
* **避坑法则**：确立“原子交付清单”。以后无论做任何一个新工具，流程必须前置绑定：从定义目录项（`slug`, `route`, `availability: "live"`）开始，再到写引擎与页面，目录注册不再是最后补救的动作，而是开发的第一步。

### 3. 样式反复覆盖（“打补丁”而非“定契约”）
* **深层原因**：出现视觉偏差时，习惯性在最末尾追加局部的类名去修补，导致后写的 CSS 意外冲刷掉了先前的 3D 高光、内阴影与悬停动效；对 Flex/Grid 的高度机制理解存在假设偏差，把“顶部水平对齐”误作“卡片等高拉伸”。
* **避坑法则**：样式必须建立在不变的底层契约（Universal Primitives）之上。不为每个小模块发明新样式，统一走 `[class*="-card"]`、`.button--primary`、`.segmented-control`。改动样式前先检查现有选择器权重，坚决不做破坏已有约定的暴力覆盖。

## 自动化防错与自检检查单（Checklist：上线前四步死命令）

1. **注册先行（Registration First）**：进入 `lib/calculators/catalog.ts`，新增计算器必须直接标注为 `availability: "live"` 并绑定具体路由。
2. **继承图元（Inherit Primitives）**：卡片容器一律统一使用 `*-card`，按钮一律统一使用 `.button.button--primary` / `.button.button--ghost`，分段选择器采用标准 `label + input + span` 结构，零手写孤立 CSS。
3. **几何自检（Geometry Check）**：
   * 左右两栏卡片顶部外边距必须归零（`margin-top: 0`），网格对齐必须为 `align-items: start`。
   * 卡片高度自然包裹（`height: auto`），禁止硬性拉伸破坏内边距节奏。
4. **编译门禁（Gatekeeper）**：终端操作完成后，依次执行：
   ```bash
   npm run typecheck && npm run test && npm run build:app
   ```
   只要这三步没有一键全绿，绝不交付用户验收。

---

## 5. 环境自动化与零手动切换红线 (Zero Manual Drift Policy)
* **核心禁忌**：严禁出现“本地开发改一套代码、发布上线前再手动改一套代码”的操作习惯。人脑不是编译器，手动切换必然遗漏。
* **规约实现**：
  1. 所有环境差异（如本地 Node.js 运行时 vs 线上静态生成 `out/`）必须统一在代码中通过环境变量（如 `process.env.NODE_ENV === "production"`）自感知。
  2. 开发人员无论在本地运行 `npm run verify`，还是远端流水线执行构建，执行的逻辑必须百分之百一致。推流即上线，零手动介入。
